# Product — Invoice Keeper (AEZA)

[AGENTS.md](../AGENTS.md) · [infra](infra.md) · [design](design.md) · [pitch](pitch.md) · [qa](qa.md)

**Статус:** одна установка — одна организация. Согласовано как on-prem кейса, 2026-10-24.

**Живой адрес:** https://rekeeper.ru. Тот же `infra/docker-compose.yml`, отличия только в `.env`.

## Идея

**Инбокс обязательств** — очередь действий, не журнал:

- сверху то, что нужно сделать: просрочено → скоро → остальное;
- пункт = период («Сервер · ноябрь · $40 · до 12.11»), не шаблон;
- закрыл — ушёл из инбокса, история жива;
- **Telegram = второй экран** того же инбокса (карточка + «Оплачено»).

Фраза: «Напомнил в Telegram — закрыл в один клик — история не потерялась.»

Не делаем: бухгалтерию, банк, конвертацию, OCR. Курс ЦБ рядом с USD и EUR только справочный. «Оплачено» = подтверждение человеком. Ассистент не советует: факты из базы, запись только после «Подтвердить». См. [assistant.md](assistant.md).

## Кто

Одна компания. Отделы — строки таблицы `teams`, в интерфейсе «отдел». Человек может быть в нескольких отделах, в шапке переключатель.

| Роль | Что может |
|------|-----------|
| Владелец | один, из `OWNER_EMAIL` / `OWNER_PASSWORD` (если пусто — `ADMIN_*`). Отделы, админы, все платежи, страница «Организация». Почту, пароль и имя из панели и `/me` сменить нельзя (403). Сброс пароля: `OWNER_RESET_PASSWORD=true` на один запуск |
| Админ отдела | в своём отделе то же, что владелец, кроме чужих отделов и учётки владельца. Людей создаёт только в своём отделе |
| Пользователь | платежи своих отделов, оплата, отмена, правка фактической даты. Те же границы в API |

Публичной регистрации, самосоздания организации и передачи владения нет. Вход — `POST /auth/login`. Сброс пароля и смена почты — код на почту. Новый человек: владелец или админ создаёт его без пароля и копирует личную ссылку-приглашение (`GET`/`POST /users/{id}/invite`), письма нет. По ссылке человек задаёт пароль (`POST /auth/invite/{token}`), входит и видит необязательную привязку Telegram. Ссылка живёт до использования или до новой. `POST /users` с паролем по-прежнему создаёт учётку с временным паролем.

Владелец создаётся при старте API всегда, не только при `SEED_DEMO`. Смена `OWNER_EMAIL` не переносит владение и не заводит второго владельца. Пароль перезаписывается только при `OWNER_RESET_PASSWORD=true`.

## Логика (из брифа)

1. Шаблон ≠ период. У периода свой снимок: название, сумма, валюта, срок. Правка шаблона трогает только будущие неоплаченные со сроком от сегодня. Периодичность задаёт админ: месяц (по умолчанию), каждые N месяцев, год, разово. День берётся из «даты ближайшей оплаты». Нет числа → последний день месяца.
2. Просрочка не стопает следующий период. Архив не создаёт новые периоды и не прячет старый долг: его видно в инбоксе и итогах, его можно оплатить. Повтор просрочки архивного платежа по умолчанию остаётся.
3. Оплата в день срока — вовремя. Правка фактической даты пересчитывает просрочку, не двигает срок и не меняет, кто оплатил. Фактическая сумма периода по умолчанию равна плановой; бюджет «факт» считает её.
4. Напоминания: T-7, T-3, в день срока молчим, просрочка на следующий день, затем каждые N дней (по умолчанию каждый день). Каждое событие один раз (период + событие + канал + получатель). Платёж внутри окна получает только ближайшую точку. Несколько просроченных периодов одного платежа — одно сводное сообщение. Оплаченный молчит. Копия просрочки — админам отдела и владельцу, если включено.
5. Часовой пояс, каденция и копия владельцу — настройки организации. Дефолты из `.env`, дальше из базы. Страница только у владельца.
6. RUB/USD/EUR, итоги раздельно, без курса. CSV для бухгалтера: `GET /payment-occurrences/export.csv`, UTF-8 BOM, разделитель `;`.

## Каналы

Почта по умолчанию включена. Личный Telegram — после привязки. Выбор: «только мои платежи» (`notify_scope=mine`, по умолчанию) или «все платежи отдела», и просрочки в личку да/нет. Выключенный тумблер Telegram молчит и для ответственного. Чат отдела просрочку получает всё равно.

По умолчанию ответственный получает личное напоминание, чат отдела — общее. Дедуп: период, событие, канал, получатель.

Привязка Telegram одна: «Оплачено» и личные напоминания. Ссылка привязки живёт до использования или до новой, админ копирует её в «Людях» и может отвязать Telegram человека. «Оплачено» в чате пишет оплату на нажавшего, если он привязан и в отделе. Иначе бот присылает ссылку привязки и оплату не ставит.

Без `TELEGRAM_BOT_TOKEN` и без SMTP остальное работает. Канал в интерфейсе показан как не настроенный.

## Процессы

Код — модули одного репозитория. Контейнеры: `web`, `api`, `worker`, `bot`, `assistant`, `db`, `caddy`. Рядом служебный `backup`.

- `api` не ходит в Telegram и не зависит от `bot` и `assistant`.
- `worker` держит горизонт периодов, письма и webhook. Карточки Telegram кладёт в outbox.
- `bot` забирает outbox, long polling, «Оплачено», привязки. Имя для t.me — из getMe в базе или `TELEGRAM_BOT_USERNAME`.
- `assistant` — отдельный процесс. Стартует, только если в `.env` есть `COMPOSE_PROFILES=assistant` (рядом с ключом GigaChat). Голос — если задан ещё и SpeechKit. ffmpeg только в его образе.

`GET /api/v1/features` говорит панели, включён ли ассистент и отвечает ли процесс. Упавший ассистент не останавливает кейс: в чате и в боте «Кип временно недоступен».

Запись ассистента — только после «Подтвердить» и теми же функциями, что обычные эндпоинты. Сессия пользователя та же.

## Демо

`SEED_DEMO=true` и в базе ещё нет отделов: владелец, админ `maria@invoice.local`, пользователь `ivan@invoice.local`. «Бухгалтерия»: аренда RUB, электричество RUB с фактической суммой, подписка EUR. «Инфраструктура»: сервер USD, домен RUB раз в год, SSL поквартально. Сид помечает уже назревшие напоминания отправленными и не шлёт пачку. Пароли в [README](../README.md).

Для показа — `python -m app.demo_data` в контейнере api, вручную. Хостинг-компания: «Инфраструктура», «Разработка», «Офис», «Маркетинг», «Поддержка»; все периодичности, оплаты разными людьми с опозданиями и фактическими суммами, архив с долгом и без. Личные письма демо-людей выключены, Telegram не привязан. Подробнее в [README](../README.md).

Сценарий жюри: вход владельца → платёж → напоминание → вход пользователя и «Оплачено» → просрочка → правка даты → следующий период.
